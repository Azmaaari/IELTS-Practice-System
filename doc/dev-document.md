# 方案二：预制JSON题库方案

## 1. 方案概述

### 1.1 核心理念
本方案预先将150篇雅思阅读文章提取成标准化JSON格式，通过纯前端技术实现完全离线的机考练习平台。用户可以通过搜索功能选择单篇练习，或让系统随机组合P1/P2/P3各一篇形成完整套题，完全模拟真实考试场景。

### 1.2 技术栈
- **框架**: Vue
- **状态管理**: Pinia
- **路由**: Vue Router
- **UI组件**: 考试页面基于现有CSS架构的自定义组件；其余可考虑element PLUs
- **离线支持**: PWA + Service Worker + Workbox
- **搜索引擎**: Fuse.js (轻量级模糊搜索)
- **构建工具**: Vite
- **类型检查**: TypeScript

### 1.3 适用场景
- 系统化备考，需要完整题库
- 希望离线使用，不依赖网络
- 需要模拟真实考试环境（套题练习）
- 想要精准搜索特定文章主题或题型

## 2. 数据安全策略：混淆 + 按需加载

### 2.1 防逆向

纯前端项目无法做到100%防止数据提取，通过**多层防护**提高爬取和批量获取的难度，让普通用户难以轻易获取完整题库。

#### 防护层次设计

```
┌─────────────────────────────────────────────────────────┐
│ 第1层：数据拆分存储                                        │
│ - 150篇文章分散在多个JSON文件中                           │
│ - 文件名混淆（hash命名，不包含语义信息）                    │
│ - 元数据与内容分离                                        │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│ 第2层：按需动态加载                                        │
│ - 只在用户选择具体文章时才加载对应JSON                      │
│ - 采用动态import()，不在初始bundle中                       │
│ - 加载路径通过算法动态计算                                 │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│ 第3层：代码混淆                                           │
│ - 字段名混淆（passage → p, questions → q）                │
│ - 压缩JSON，去除空格和换行                                │
│ - Base64编码                                      │
└─────────────────────────────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────┐
│ 第4层：运行时检测                                         │
│ - 检测开发者工具打开状态                                   │
│ - 检测频繁的网络请求（防批量下载）                         │
│ - 添加时间戳和会话标识                                     │
└─────────────────────────────────────────────────────────┘
```

### 2.2 例：数据文件组织结构

```
public/
└── data/
    ├── manifest.json              # 题库索引（混淆后）
    ├── chunks/
    │   ├── a3f5b2.json           # P1难度的一组文章（5-10篇）
    │   ├── d8e1c4.json           # P1难度的另一组
    │   ├── b7k9m3.json           # P2难度的一组
    │   ├── ...                   # 共约15-20个chunk文件
    │   └── z9x2v8.json
    └── search-index.json          # 搜索索引（仅标题）
```

### 2.3 Manifest索引设计

**manifest.json** 只包含必要的元数据，不包含完整内容：

```json
{
  "version": "1.0.0",
  "totalExams": 150,
  "lastUpdated": "2025-10-16",
  "index": [
    {
      "id": "e1",
      "t": "The History of Timekeeping",  // 标题
      "d": 1,                              // 难度：1=P1, 2=P2, 3=P3
      "qc": 13,                            // 题目数量
      "qt": ["mc", "tfng", "match"],       // 题型缩写
      "c": "a3f5b2",                       // 所在chunk文件
      "o": 0                               // 在chunk中的偏移量
    }
    // ... 共150条
  ]
}
```

**字段混淆映射表**（仅存在于源码中）：
- `t` = title
- `d` = difficulty
- `qc` = questionCount
- `qt` = questionTypes
- `c` = chunk
- `o` = offset

### 2.4 Chunk文件设计

每个chunk包含5-10篇文章，进一步混淆：

```json
{
  "v": "1.0",
  "data": [
    {
      "p": {
        "t": "The History of Timekeeping",
        "para": [
          {"l": "A", "c": "For thousands of years..."},
          {"l": "B", "c": "The ancient Egyptians..."}
        ]
      },
      "q": [
        {
          "n": 1,
          "ty": "mc",
          "txt": "What is the main topic?",
          "opt": ["A", "B", "C", "D"],
          "ans": "b"
        }
      ]
    }
    // ... 更多文章
  ]
}
```

### 2.5 动态加载机制

**加载流程**：

1. **应用启动** → 只加载 `manifest.json`
2. **浏览** → 显示150篇文章的标题和元数据
3. **选择文章** → 计算chunk路径 → 动态加载对应chunk
4. **解析数据** → 从chunk中提取目标文章 → 渲染练习页面

**关键技术点**：

- **动态导入路径计算**：根据文章ID计算chunk文件名，而不是硬编码映射表
- **缓存策略**：已加载的chunk缓存在内存中，避免重复请求

### 2.6 运行时防护

**检测开发者工具**：
```
原理：检测window.outerHeight与innerHeight差异
行为：检测到时暂停数据加载（不强制关闭，避免影响体验）
其它：禁用f12
```

**频率限制**：
```
限制：5分钟内最多加载20个不同的文章
目的：防止脚本批量下载
实现：localStorage记录加载时间戳
```

**数据指纹**：
```
每次加载的JSON数据附加session标识
后续操作验证标识一致性
防止数据被复制到其他会话
```

## 3. 核心功能设计

### 3.1 搜索功能

#### 3.1.1 搜索策略

模糊搜索，支持以下维度：

- **标题搜索**：匹配文章标题关键词
- **难度筛选**：P1 / P2 / P3

#### 3.1.2 搜索索引构建

**search-index.json** 结构（简化版）：

```json
{
  "version": "1.0",
  "items": [
    {
      "id": "e1",
      "title": "The History of Timekeeping",
      "difficulty": 1,
      "questionCount": 13
    }
    // ... 150条
  ]
}
```

**索引大小优化**：
- 只保留标题和基本元数据
- 压缩后约20-30KB
- 应用启动时一次性加载

#### 3.1.3 搜索UI设计

```
┌────────────────────────────────────────────────────────┐
│  🔍  搜索文章标题或主题...              [搜索按钮]        │
└────────────────────────────────────────────────────────┘
┌────────────────────────────────────────────────────────┐
│  筛选：                                                  │
│  难度： [ ] P1   [ ] P2   [ ] P3                        │
│  
└────────────────────────────────────────────────────────┘
```

**搜索体验优化**：
- 实时搜索（输入时防抖300ms）
- 高亮匹配关键词
- 显示匹配度分数
- 支持拼音搜索（可选）

### 3.2 套题组合功能

#### 3.2.1 真实考试规则

雅思阅读考试规则：
- **总时长**：60分钟 （倒计时）
- **文章数量**：3篇
- **难度分布**：P1（简单）、P2（中等）、P3（难）
- **题目总数**：40题（每篇13-14题）
- **题型分布**：混合多种题型

#### 3.2.2 组题算法

**随机组题策略**：

1. **分层抽取**：
   - 从P1文章池中随机抽取1篇
   - 从P2文章池中随机抽取1篇
   - 从P3文章池中随机抽取1篇

2. **去重机制**：
   - 记录用户最近练习的文章ID
   - 组题时优先选择未练习过的文章
   - 如果全部练习过，则重新随机

3. **题型平衡**（可选）：
   - 检查3篇文章的题型分布
   - 确保包含多样化题型
   - 避免某种题型过度集中

#### 3.2.3 套题练习流程

```
开始套题
    ↓
[确认页面]
显示：P1: 文章标题1
     P2: 文章标题2
     P3: 文章标题3
     预计用时：60分钟
     [开始练习] [重新随机]
    ↓
[练习页面]
- 60分钟倒计时
- 切换文章标签（P1 / P2 / P3）
- 统一提交
    ↓
[成绩页面]
- 总分：XX/40
- 分项得分：P1: 12/13, P2: 11/13, P3: 10/14
- 错题分析
```

#### 3.2.4 单篇练习流程

用户也可以选择单篇文章单独练习：

```
浏览文章列表
    ↓
选择某篇文章
    ↓
[练习页面]
- 20分钟倒计时（可暂停）
- 单篇完整练习
- 提交后立即查看结果
```

### 3.3 练习历史与统计

#### 3.3.1 数据存储设计

使用 **IndexedDB** 存储练习记录：

**数据结构**：

```typescript
SessionRecord {
  id: string (自动生成)
  type: 'single' | 'full-test'  // 单篇 or 套题
  timestamp: number
  duration: number  // 实际用时（秒）
  
  // 单篇练习
  examId?: string
  score?: number
  totalQuestions?: number
  
  // 套题练习
  exams?: [
    { examId: string, difficulty: 1|2|3, score: number, total: number }
  ]
  totalScore?: number
  totalQuestions?: number
  
  // 答题详情
  answers: Record<string, any>
  correctAnswers: Record<string, any>
  
  // 分析数据
  questionTypeStats: {
    'multiple-choice': { correct: number, total: number },
    'true-false-ng': { correct: number, total: number },
    // ...
  }
}
```

#### 3.3.2 统计维度

**全局统计**：
- 总练习次数
- 总练习时长
- 平均正确率

**文章记录**：
- 已练习文章列表
- 每篇文章的练习次数和最好成绩
- 未练习文章数量

#### 3.3.3 做题记录完整保留方案

**核心需求**：用户查看历史记录时，需要完整恢复当时的答题状态，包括：
- 用户选择的所有答案
- 文章中的高亮标记
- 笔记内容

**数据结构设计**：

```json
{
  "id": "session_123456",
  "examId": "e1",
  "timestamp": 1697461200000,
  "type": "single",
  
  "answers": {
    "q1": "b",
    "q2": "true",
    "q3": "not given"
  },
  
  "highlights": [
    {
      "paragraphLabel": "A",
      "startOffset": 45,
      "endOffset": 78,
      "text": "For thousands of years",
      "color": "yellow"
    },
    {
      "paragraphLabel": "C",
      "startOffset": 120,
      "endOffset": 155,
      "text": "ancient civilizations",
      "color": "yellow"
    }
  ],
  
  "notes": "这段讲的是古代计时方法的演变...",
  
  "score": 11,
  "totalQuestions": 13,
  "duration": 1245
}
```

**高亮恢复机制**：

1. **保存时**：记录高亮文本的段落标识和偏移量
2. **恢复时**：根据段落和偏移重新渲染高亮
3. **兼容性**：如果文章内容有修改，通过模糊匹配尝试恢复

**查看历史记录流程**：

```
用户点击历史记录
    ↓
加载完整的SessionRecord
    ↓
重新加载该篇文章数据
    ↓
进入"回顾模式"（只读）
    ↓
渲染页面：
  - 恢复所有答案选择状态
  - 重新应用高亮标记
  - 显示笔记内容
  - 显示正确/错误标识
    ↓
用户可以对比自己的答案和正确答案
```

### 3.4 题型渲染系统

## 4. localStorage容量管理方案

### 4.1 容量问题分析

**localStorage限制**：
- 大多数浏览器：5-10MB
- 存储内容：练习记录、高亮、笔记、用户设置

**容量占用估算**：
- 单条练习记录（含答案+高亮+笔记）：约5-10KB
- 150篇文章全部练习一遍：约1.5MB
- 多次重复练习：可能超过限制

### 4.2 存储策略设计

**分层存储方案**：

```
localStorage (轻量数据)
├── 用户设置 (~5KB)
├── 最近10条练习记录 (~100KB)
└── 全局统计数据 (~10KB)

IndexedDB (大容量数据)
├── 完整练习历史 (无上限)
├── 详细高亮记录 (无上限)
└── 笔记内容 (无上限)
```

**数据存储规则**：

1. **localStorage存储**：
   - 用户配置（主题、字体大小等）
   - 最近10条练习的快速索引
   - 当前练习的临时数据（未提交）

2. **IndexedDB存储**：
   - 所有历史练习记录
   - 完整的高亮和笔记数据
   - 可以存储数百MB甚至GB的数据

### 4.3 数据清理策略

**自动清理机制**：

1. **保留策略**：
   - 最近30天的记录：全部保留
   - 30-90天的记录：保留但压缩（去除详细高亮）
   - 90天以上：只保留基本得分统计

2. **手动清理**：
   - 设置中提供"清理历史记录"选项
   - 可选择清理时间范围
   - 导出后再清理

3. **容量监控**：
   - 实时显示存储使用情况
   - 接近限制时提示用户
   - 提供一键导出备份功能

### 4.4 数据导出与恢复

**导出功能**：
- 一键导出所有练习记录为JSON文件
- 用户可保存到本地或云盘
- 文件大小：完整历史约5-20MB

**导入功能**：
- 支持导入之前导出的JSON文件
- 自动合并，去重
- 恢复高亮和笔记

## 5. PWA离线支持

### 5.1 PWA核心特性

**目标**：用户首次访问后，可以完全离线使用整个应用和所有题库。

**关键能力**：
- 离线访问应用
- 离线加载文章数据
- 离线记录练习结果

### 5.2 Service Worker策略

#### 5.2.1 缓存策略设计

使用 **Workbox** 简化Service Worker开发：

**缓存分层**：

1. **App Shell（应用外壳）**
   - HTML、CSS、JS主文件
   - 策略：Cache First（优先使用缓存）
   - 更新：应用版本更新时强制刷新

2. **静态资源**
   - 字体、图标、图片
   - 策略：Cache First
   - 有效期：长期缓存

3. **数据文件**
   - manifest.json、chunk文件、search-index.json
   - 策略：Network First（优先网络，失败用缓存）
   - 更新：检测版本号，增量更新

4. **运行时缓存**
   - 用户加载过的chunk文件
   - 策略：Cache First
   - 容量限制：最多缓存所有150篇文章数据（约5-10MB）

#### 5.2.2 预缓存策略

**首次安装时预缓存**：
- App Shell（必需）
- manifest.json（必需）
- search-index.json（必需）
- 不预缓存chunk文件（按需加载）

**后台同步**：
- 用户空闲时，后台逐步缓存热门chunk
- 或提供"下载全部题库"按钮，让用户主动触发

#### 5.2.3 版本更新机制（发包更新）

**更新模式说明**：
- **不使用服务器**：每次版本更新通过重新部署整个应用
- **发包形式**：类似APP更新，用户需要刷新或重新访问网站
- **无增量更新**：每次更新都是完整的新版本

**版本检测机制**：

```
用户访问应用
    ↓
Service Worker检查本地缓存版本
    ↓
与manifest.json中的版本号对比
    ↓
如果版本号不同：
    ↓
[显示更新提示]
"发现新版本 v1.2.0（新增20篇文章）"
[立即更新] [稍后提醒]
    ↓
用户点击"立即更新"
    ↓
清除所有旧缓存
    ↓
Service Worker下载所有新资源
    ↓
重新加载页面
```

**版本号管理**：
- 在`vite.config.ts`中配置版本号
- 构建时自动写入manifest.json
- 每次发布前手动递增版本号

**用户体验优化**：
- 不强制更新，用户可以选择"稍后提醒"
- 下载新版本时显示进度条
- 更新完成后显示"更新日志"

### 5.3 离线体验优化

**离线指示器**：

- 顶部显示在线/离线状态
- 离线时禁用需要网络的功能（如果有）

**数据同步**：
- 虽然不支持多设备同步
- 但可以导出/导入练习记录（JSON文件）
- 用户可以手动备份到云盘

**存储空间管理**：
- 显示当前缓存大小
- 提供清除缓存选项
- 设置中可选择"完整缓存"或"按需加载"

### 6.2 核心数据流

#### 6.2.1 搜索选择文章流程

```
用户输入搜索关键词
    ↓
useSearch 从 search-index.json 中模糊匹配
    ↓
返回匹配结果列表（只包含元数据）
    ↓
用户点击某篇文章
    ↓
useExamLoader 根据文章ID查询 manifest
    ↓
计算所在的chunk文件名
    ↓
检查内存缓存是否已加载该chunk
    ├─ 已缓存 → 直接从缓存提取
    └─ 未缓存 → 动态加载chunk文件
    ↓
解析JSON，提取目标文章数据
    ↓
存入 examStore.currentExam
    ↓
路由跳转到 /practice/:id
    ↓
渲染练习页面
```

#### 6.2.2 随机套题流程

```
用户点击"开始套题练习"
    ↓
useRandomSet.generateFullTest()
    ↓
从 manifest 中分别筛选 P1/P2/P3 文章
    ↓
排除最近练习过的文章（从 historyStore 获取）
    ↓
每个难度随机选1篇，共3篇
    ↓
显示确认页面（文章预览）
    ├─ 用户点击"重新随机" → 返回重新生成
    └─ 用户点击"开始" → 继续
    ↓
批量加载3篇文章数据（可能跨多个chunk）
    ↓
存入 practiceStore.fullTestSession
    ↓
路由跳转到 /practice/full-test
    ↓
渲染套题练习页面（包含3个标签页）
```

#### 6.2.3 答题与评分流程

```
用户在练习页面答题
    ↓
每个题目组件收集答案到 practiceStore.userAnswers
    ↓
practiceStore 实时更新"已答题状态"
    ↓
底部导航栏同步更新（已答题目高亮）
    ↓
用户点击"Submit"
    ↓
useGrading.grade(userAnswers, correctAnswers)
    ↓
计算总分、分项得分、题型正确率
    ↓
生成详细结果报告
    ↓
保存到 historyStore（持久化到IndexedDB）
    ↓
更新全局统计数据
    ↓
显示成绩页面
```

### 8.2 数据准备流程

**步骤1：人工提取**
- 从PDF或现有题库中提取150篇文章
- 按照标准JSON格式手工录入或使用工具辅助

**步骤2：数据验证**
- 检查JSON格式正确性
- 验证答案准确性
- 确保题号连续
- 统计题型分布

**步骤3：数据处理**
- 生成唯一ID（e001-e150）

**步骤4：数据分组**
- 将150篇文章按难度分组
- 每5-10篇打包成一个chunk
- 生成manifest索引

**步骤5：混淆处理**
- 压缩JSON（去除空格）
- 字段名混淆
- 生成hash文件名

**步骤6：构建集成**
- 将chunk文件放入public/data/chunks/
- 生成manifest.json和search-index.json
- 配置Vite构建脚本

## 9. 技术实现要点

### 9.1 动态chunk加载

**挑战**：Vite在构建时需要静态分析import()路径

**解决方案**：

方案A：使用public目录 + fetch
- chunk文件放在public/data/chunks/
- 运行时通过fetch动态加载
- 不经过Vite处理，直接部署

方案B：使用动态import + 路径映射
- 在src/assets/data/chunks/目录
- 使用Vite的glob import功能
- 构建时打包，运行时按需加载

**推荐使用方案A**，因为：
- 更灵活，方便混淆和拆分
- 不增加构建复杂度
- 便于Service Worker缓存控制

### 9.2 搜索性能优化

**Fuse.js配置优化**：

- 设置合理的threshold（模糊度）：0.3
- 限制搜索字段：只搜索title和keywords
- 限制返回结果：最多50条
- 使用debounce避免频繁搜索

**大数据量优化**：

虽然只有150篇，但如果未来扩展到1000+篇：
- 考虑使用Web Worker进行搜索
- 或者分批加载搜索索引
- 实现虚拟滚动显示结果列表

### 9.3 练习状态管理

**单篇练习**：

- 使用practiceStore存储当前会话
- 包含：文章数据、用户答案、计时器状态
- 刷新页面时从localStorage恢复

**套题练习**：

- 存储3篇文章的完整数据
- 标签切换时保持各自的答案状态
- 全局计时器持续运行
- 支持中途暂停（保存到localStorage）

**状态恢复**：

用户刷新页面或关闭后重新打开：
- 检测是否有未完成的练习会话
- 提示用户"继续上次练习"或"开始新练习"
- 恢复倒计时、答案、滚动位置

### 9.4 题型渲染优化

**动态组件加载**：

```
<component 
  :is="getQuestionComponent(question.type)" 
  :question="question"
  v-model="userAnswers[question.id]"
/>
```

**组件复用**：

- 相似题型共用组件（如TRUE/FALSE和YES/NO）
- 通过props传递配置差异

**性能优化**：

- 使用虚拟滚动（如果题目很多）
- 懒加载题目图片（如果有）
- 避免不必要的响应式数据

### 10.2 免费部署平台详细对比

考虑到有一定的用户量，以下是推荐的免费部署平台：

#### 平台对比表

| 平台 | 免费额度 | 带宽限制 | 访问速度 | CDN | 自定义域名 | 推荐指数 |
|------|---------|---------|---------|-----|-----------|---------|
| **Vercel** | 无限项目 | 100GB/月 | ⭐⭐⭐⭐⭐ | 全球CDN | 支持 | ⭐⭐⭐⭐⭐ |

#### 详细说明

**1. Vercel（最推荐）**
- **优点**：
  - 部署极快（通常30秒内完成）
  - 全球CDN，中国访问速度尚可
  - 自动HTTPS
  - 支持环境变量
  - 可以绑定多个自定义域名
- **限制**：
  - 每月100GB带宽（对中小规模用户量足够）
  - 单个文件最大50MB
- **适合场景**：需要快速迭代，频繁更新

**2. Netlify（同样推荐）**
- **优点**：
  - 功能和Vercel类似
  - 提供更多的构建时间（每月300分钟 vs Vercel的100分钟）
  - 支持表单提交（可用于收集反馈）
- **限制**：
  - 每月100GB带宽
  - 构建时间：每月300分钟
- **适合场景**：需要额外功能（如表单、A/B测试）

**3. Cloudflare Pages（国内用户首选）**
- **优点**：
  - **无限带宽**（最大优势）
  - 全球CDN，国内访问速度极快
  - 与Cloudflare生态集成
  - 免费SSL证书
- **限制**：
  - 每月500次构建
  - 单次构建最多20分钟
- **适合场景**：**预期用户量较大，或有国内用户**

**4. GitHub Pages**
- **优点**：
  - 简单易用，与GitHub仓库深度集成
  - 适合开源项目
  - 完全免费
- **缺点**：
  - 国内访问速度较慢（可能需要加速）
  - 功能较基础
- **适合场景**：个人项目，不追求极致性能

#### 推荐方案

**考虑到您的需求（有一定用户量 + 纯前端）**：

**首选：Cloudflare Pages**
- 无限带宽，无需担心流量问题
- 国内外访问速度都很快
- 部署简单：连接GitHub仓库，自动构建

**备选：Vercel 或 Netlify**
- 如果用户主要在海外
- 需要更多开发者工具和功能

### 10.3 Cloudflare Pages部署步骤

**1. 准备工作**
- 注册Cloudflare账号（免费）
